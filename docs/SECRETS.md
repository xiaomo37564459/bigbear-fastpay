# 敏感信息怎么处理（往仓库里写东西之前，先看这一页）

**这个仓库是公开的。** 任何人都能看到里面的每一个字，包括历史版本。

所以只有一条总规矩：

> **能被别人拿去直接登录、直接连上、直接冒充你的东西，一个字都不许进仓库。**
> 剩下的东西，公开出去没有实际损失，不用为它折腾。

下面把「哪些是哪些」列清楚，照着判断就行。

---

## 一、三档清单：写之前对一眼

### ✅ 可以写（放心写，不用打码）

| 类型 | 例子 |
| --- | --- |
| 域名、网址 | `https://pay.copliot.cloud`、`https://pay.copliot.cloud/fastpay-admin/` |
| 端口号 | `7001`、`5432`、`443` |
| 占位符 | `<数据库地址>`、`<用户名>`、`YOUR_MERCHANT_NO` |
| 一眼假的示例值 | `demo` / `123456`、`M17390000123400`、`abc` |
| 服务器上的路径、服务名、文件权限 | `/opt/fastpay/`、`fastpay-server`、`640 root:fastpay` |
| 系统版本、依赖版本 | `OpenCloudOS 9.4`、`PostgreSQL 15`、`JDK 17` |

理由：这些东西要么本来就公开（域名任何人都查得到），要么单独拿到手什么也做不了。

### ❌ 绝对不许写（写进去 = 事故，发现了立刻处理）

| 类型 | 例子（**这些是坏例子，别照抄格式往里填真值**） |
| --- | --- |
| 数据库账号密码 | `DB_USERNAME=fastpay` + `DB_PASSWORD=真实口令` |
| 各种密钥、私钥 | `FASTPAY_JWT_SECRET=`、API Secret、SSH 私钥、SSL 私钥、`.pem` / `.key` 文件 |
| 后台 / 商户 / 服务器的真实登录口令 | 任何一个真的能登进去的账号+密码组合 |
| 真实的内网地址、内部拓扑 | `10.x.x.x`、`172.x.x.x`、内网机器名、内部服务之间怎么连 |
| **任何人的真实登录邮箱或账号名** | 需求方的邮箱、同事的邮箱、真实用户手机号 |
| 真实的订单号、用户数据 | 从生产库里导出来的任何一行 |

这一档没有「情有可原」的情况。**要写进文档的，一律换成占位符。**

### ⚠️ 可以写，但要克制（不必回头去擦，新写的时候别习惯性写死）

| 类型 | 怎么把握 |
| --- | --- |
| **服务器公网 IP** | 域名 `pay.copliot.cloud` 本来就公开，任何人敲一条 `nslookup` 就知道背后是哪台机器，**藏不住也不用藏**。所以：<br>· 已经写在文档里的，**不用专门去擦**，为它改一遍历史更不划算<br>· **新写文档时优先用域名或 `<服务器>` 占位符**，别顺手写死 IP<br>· 真正决定安全的是那台机器的门结不结实，不是文档里写没写地址 |

## 二、提交之前自己扫一遍

`git commit` 之前，在仓库根目录跑一下：

```bash
# 扫本次改动里有没有明显的敏感值
git diff --cached | grep -inE 'password\s*[:=]|passwd\s*[:=]|secret\s*[:=]|api[_-]?key|private[_-]?key|BEGIN .*PRIVATE KEY'

# 扫有没有内网地址
git diff --cached | grep -nE '(^|[^0-9])(10\.|192\.168\.|172\.(1[6-9]|2[0-9]|3[01])\.)[0-9]'

# 扫有没有真实邮箱（占位符里的 example.com / your-domain 不算）
git diff --cached | grep -inE '[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}' | grep -viE 'example\.(com|org)|your-domain|@fastpay|noreply'
```

有输出就一条条看清楚再决定。**扫出来是好事，说明它拦住了。**

`.gitignore` 里已经排除了 `.env`、`*.key`、`*.pem` 这类文件，但**不要指望 `.gitignore` 兜底** —— 它只挡文件名，挡不住你把密码写进 `.md` 里。

## 三、万一已经写进去了怎么办

按这个顺序，**顺序不能反**：

1. **先当作已经泄露** —— 公开仓库被爬虫扫是秒级的，"我马上就删" 没有意义。
2. **立刻换掉那个东西**：改数据库密码、重新生成 JWT 密钥（`openssl rand -hex 48`）、换 SSH 密钥。**换掉之后，泄露的那份就变成一串废字符了，这才是真正的止血。**
3. 再把仓库里的内容清掉，正常提交即可。
4. **要不要重写 git 历史，由总指挥决定，不要自己动手。** 重写历史会让所有人手上的副本全部作废，代价很大；只有在泄露的东西**换不掉**（比如别人的隐私数据）时才值得。

## 四、那真实的密码、密钥到底放哪

**唯一存放点：那台服务器上，只有 root 能读的文件。**

分两类：

### 1. 程序运行要用的（数据库口令、JWT 密钥等）

放 `/etc/fastpay/fastpay-server.env`，权限 `640 root:fastpay`。
这个已经是现状，细节见 [部署说明](DEPLOY.md) 第二节。程序只从这里读，仓库里一律是占位符。

### 2. 人要用的（后台账号口令、第三方账号等）

放 `/root/fastpay-ops/credentials.md`，权限 `600 root`（**只有 root 能读**）。

| 问题 | 答案 |
| --- | --- |
| **存在哪** | 服务器 `/root/fastpay-ops/credentials.md`，`chmod 600` |
| **谁能拿** | 能用 SSH 密钥登上这台服务器的人 —— 也就是运维。不另发一套权限，**"能登服务器" 本身就是这道门** |
| **怎么拿** | `ssh root@<服务器> 'cat /root/fastpay-ops/credentials.md'` |
| **换了怎么同步** | 谁改谁负责改这个文件。改完在 issue 里只写一句「XX 的口令已更新，请重新取一次」，**绝不写新值** |
| **要写什么** | 每条写清：这是哪个系统的、账号是什么、什么时候改的、谁改的。**只有这个文件里可以有明文** |

这个文件只存在于服务器上，仓库里查不到它建没建。**第一个要往里存口令的人负责建**，建的时候把权限一并设好：

```bash
ssh root@<服务器> 'mkdir -p /root/fastpay-ops \
  && touch /root/fastpay-ops/credentials.md \
  && chmod 600 /root/fastpay-ops/credentials.md'
```

每条按上面「要写什么」那一行的格式写：哪个系统、账号是什么、什么时候改的、谁改的。

> ⚠️ **它只存在于那一台服务器上，机器没了口令就一起没了。**
> 这个文件不做备份是故意的 —— 备份到哪儿，哪儿就多一个泄露点。
> 所以真正要紧的口令，**请自己在个人密码管理器里也留一份**，别把这台机器当唯一的保险箱。

### 🚫 一条红线

**不许要求任何人把口令贴进 Multica 工作区的任何地方** —— issue 描述、评论、聊天、附件都不行。

这里**没有真正私密的通道**：这些内容对整个工作区可见，还会被后续所有 agent 读到、被总结、被引用。贴哪都等于公开。

需要把口令给谁，就让他自己上服务器取；他上不去服务器，那说明这件事本来就不该他做。

## 五、上线验证要进后台，用哪个账号

**先说结论：管理后台目前只支持一个管理员账号，也没有「只读」这种权限档。**

实测依据（`v1.2.0`，2026-08-19）：

- `fp_admin` 表只有 `id / username / password / nickname / avatar / status / last_login_*/ token_version / 时间戳 / deleted`，**没有角色或权限字段**
- 整个库里只有 6 张业务表，**没有角色表、权限表、菜单表**
- 后端 `AuthInterceptor` 只区分「管理员」和「商户」两种身份，**管理员之间没有任何权限差别**：只要能登进管理后台，商户增删、订单手动确认，全都能干
- 后端没有「新建管理员」的接口，前端也没有这个页面。`InitConfig` 只在**库里一个管理员都没有**的时候建第一个

**所以「给验证专用开一个只能看不能改的账号」，现在做不到。**

### 现在的办法（2026-08-20 由需求方拍板定下，MTM-190 方案 D）

一句话：**能自动查的全部自动查，不用任何账号；实在要人点的那一小块，用一个验证专用的测试商户去点。**

具体分两块：

1. **机器能查的部分，一个账号都不需要。**
   `deploy/verify-release.sh` 会把「服务活着没、版本对不对、迁移跑没跑、页面打不打得开、权限收没收紧、日志有没有报错」全查一遍。
   它靠的是 SSH 和一个**免登录**的健康检查接口（`/fastpay-server/api/health`），不碰任何业务数据。

2. **要人点的那一小块，用验证专用测试商户。**（⏳ 截至写这份文档时，这个商户**还没建**，在等需求方创建）
   - 这个商户由需求方在管理后台正常创建，**走的是系统本来就有的功能，不碰数据库**
   - 它是**空白**的，里面没有任何真实交易；建店铺、建收款通道、建收款码、下单、把订单改成已支付/已关闭，它自己全能做，不需要真钱也不需要管理员账号
   - 口令写进上面第四节说的 `/root/fastpay-ops/credentials.md`
   - **必须清楚：这个账号在它自己范围内是全权限的，不是只读的。** 用它的人自觉只看不改
   - **停用它需要管理员权限，运维自己做不到** —— 要停得请需求方在管理后台点一下。不停用风险也很低：没有真实交易数据，收款通道是假的占位配置，真收不到钱

怎么用见 [发完版怎么确认真的发好了](RELEASE_VERIFY.md)。

### 为什么不建「验证专用的管理员账号」

因为建它**只能手工往 `fp_admin` 表塞一行**（系统没有「新建管理员」这个功能），那是往生产库写数据，属于红线。

**代价要说清楚**：管理后台**自己**的功能改了（商户管理页、渠道配置页、控制台统计等），运维验不了，还得请需求方本人点一下。这个缺口是**已知且被接受的** —— 等真的反复挡事了再单独立项，现在不值得为它破红线。

需求方自己的账号密码，**运维和质检都不需要知道**，他随时可以改，不影响验证。

### 该改成什么样（要单独立改造单）

给 `fp_admin` 加一个角色字段（例如 `role`：`super` / `viewer`），后端对「写」类接口校验角色，前端把改不了的按钮藏掉。这样才是真正的只读账号，上面那个缺口也就一并补上了。

在那之前，上面的办法是最不坏的选择。

## 六、这份规矩管谁

**所有往这个仓库提交内容的人**，不分岗位 —— 写代码的、写文档的、写测试数据的，都一样。

判断不了的时候用这个笨办法：
**「如果这行字被贴到微博上，我会不会需要马上改点什么？」** 会 → 不许写。
