# 发完版怎么确认「真的发好了」

每次把新版本发到线上之后，按这一页走一遍。**一共两步**：

1. **跑一条命令** —— 机器能替你确认的事，它一次全查完
2. **登进去点一遍** —— 这一版改了什么，就点什么。这一步机器替不了

两步都过了，才算发好了。

> 这套办法是 MTM-190 定下来的（需求方选了方案 D）。核心思路是：
> **能自动化的全自动化，不需要任何账号；实在要人点的那一小块，用一个不含真实数据的验证专用商户去点。**

---

## 第一步：跑验证脚本

在自己电脑上、仓库根目录执行，把版本号换成这次发的，把 `MTM-210` 换成你这次动生产用的
操作锁令牌（就是你的 issue 编号，见 [部署说明](DEPLOY.md) 第零节）：

```bash
ssh root@<服务器> 'bash -s v1.6.0 MTM-210 prod' < deploy/verify-release.sh
```

已经登在服务器上了也行：

```bash
bash /root/fastpay-ops/verify-release.sh v1.6.0 MTM-210 prod
```

三个参数分别是：

| 第几个 | 写什么 | 不写会怎样 |
| --- | --- | --- |
| 1 | 这次发的版本号（git tag），如 `v1.6.0` | 跳过版本号比对 |
| 2 | 你这次动生产用的操作锁令牌（你的 issue 编号），如 `MTM-210` | 只把「现在谁在动这台机器」打出来看看（第 3 个参数写了 `prod` 时另说，见下） |
| 3 | 这台机器是不是生产：动生产写 `prod`，别的环境写 `test` / `staging` / `dev` | 按「没说」处理，第 7 项从宽 |

第 2 个参数可以不传（老写法照样能跑），但**建议传上**：传了它，脚本会顺便确认
「这段时间里没有别人也在动这台机器」。有别人占着锁就直接判失败 —— 因为那种情况下，
上面所有检查结果都不可信，你验的可能已经不是你发的那一版了。

**第 3 个参数动生产时也请写上 `prod`。** 写了它，第 7 项（有没有别人也在动这台机器）
会在两种真危险的情况下直接判失败，而不是只提醒一句：

| 情况 | 写了 `prod` | 没写，或写的是别的环境 |
| --- | --- | --- |
| 这台机器上压根没装操作锁脚本（`/root/fastpay-ops/prod-lock.sh`），没法确认有没有人跟你同时在动 | **判失败** | 只提醒一句，不拦你 |
| 你没传第 2 个参数（手上没锁），但这会儿**确实有别人占着锁**在动这台机器 | **判失败** | 只提醒一句，不拦你 |
| 你没传第 2 个参数，而且现在**没人**占锁 | 照常通过 | 照常通过 |

最后一行是特意留的口子：**这个脚本只读，不改任何东西**。有人纯粹上来体检一下（看看服务
活着没、版本对不对），压根没打算动生产，那就不该被拦。真危险的只有「别人正动着这台生产机器、
你却两眼一抹黑也摸上来了」这一种组合。

一刀切卡死无害操作的代价是反效果：大家学到的不是「动生产要上锁」，而是「别写 `prod` 了，
写了麻烦」—— 那这个参数就白加了。

`prod` 千万别拼错。写成认不出来的值（比如 `prd`）脚本会当场判失败并指出来 ——
故意的：拼错了你以为开了严格模式，其实没开，而这种失效一点动静都没有。

它会依次查这些，**任何一项 ❌ 就会以退出码 1 结束**，可以直接串在部署命令后面：

| 查什么 | 为什么要查 |
| --- | --- |
| 后端服务在不在跑 | 最基本的 |
| **服务启动时间是不是晚于 jar 修改时间** | 换了 jar 忘了重启 —— 最常见也最难发现的一种「发了个寂寞」 |
| 服务器记的版本号和你要发的对不对得上 | 防止传错文件、传漏文件 |
| 后端本机健康检查 200 | 程序自己活着 |
| 两个前端页面公网 200 | 用户真的打得开 |
| 公网健康检查 200 | nginx 转发也是通的 |
| 接口文档对外是 404 | 排查问题时打开过，忘了关回去 |
| 有没有全局可写的文件 | Windows 打的 tar 包解压到 Linux 会变成谁都能改，支付页被人换掉都发现不了 |
| 数据库连得上 | 连不上就什么都验不了 |
| **每一版数据库脚本跑了没有**（`V1_1` ~ `V1_5`，逐版报） | 漏跑一版，这一版修的东西就等于没修 —— 比如 `V1_4` 漏跑，「两人同价撞单认错人」那个赔钱 bug 原样还在，而且没有任何迹象 |
| 最近日志里有没有 ERROR | 起来了不代表没问题 |
| **有没有别人也在同时动这台机器** | 有的话上面每一项都不可信 —— 你验的可能已经不是你发的那一版了（2026-08-20 真撞过一次，见 MTM-210）。第 3 个参数写了 `prod` 时更严：这台机器没装操作锁、或者你手上没锁而别人正占着锁，都会判失败 |

脚本**只读**：不写数据库、不改配置、不重启服务。

### 又加了一版数据库脚本？记得给验证脚本加一行

「哪一版数据库脚本跑了没有」这一项，靠的是 `deploy/verify-release.sh` 里一张表（`MIGRATION_CHECKS=`）。

**加了新的迁移脚本，就在那张表里补一行** —— 写清楚是哪一版、去查哪张表或哪一列、缺了算失败还是只提醒、以及给人看的那句话。**下面的代码一个字都不用改**，查询语句和判定结果都是照着这张表自动生成的。格式说明就写在表上面的注释里。

> 为什么专门立这条规矩：这里最早是手写的两段 `if`，只认 `V1_1` 和 `V1_2`。后来加了 `V1_3` / `V1_4` / `V1_5`，没人记得回来补，于是这三版漏跑了脚本照样报「全部正常」。**报错还能被人看见，报绿是安安静静的** —— 尤其 `V1_4` 漏跑，等于那个「两人同价撞单认错人」的赔钱 bug 修复根本没生效，谁都不会发现（MTM-214）。现在自测里有一条专门盯着这张表，少了哪一版会直接红。

另外两条这一项自己会兜住的情况：

- **这台机器没装 `psql`、连不上库、账号口令不对** —— 一律只说「这一项查不了」，绝不会说成「迁移没跑」，也绝不会把人指去补跑迁移脚本。方向指反比不查更危险（MTM-204 / MTM-218）
- **连上了，但库里一张业务表都没有** —— 十有八九是 `DB_URL` 里的库名写错、连到别的库上去了。这时候脚本会直接说「先核对库名」，而不是一版版报「没生效」

**它也不会把数据库地址打印出来**，这点可以放心 —— 因为这份输出通常是要贴回 issue 给别人看的：

- 它读 `/etc/fastpay/fastpay-server.env` 拿数据库地址，但**绝不会把里面的值打印出来**
- 连不上数据库时**不打印 psql 的原始报错**（里面带着主机地址和账号名），只说是哪一类原因：口令不对 / 库名账号不存在 / 主机名解析不了 / 连接超时 / 端口连不上
- 日志片段这类原样透出来的内容，打印前会把地址换成 `<地址已隐去>` / `<IP已隐去>` / `<IPv6已隐去>`

要看原文，自己 SSH 上服务器看。

日志片段那一条是**三道防线叠着来**的，因为只挡一种写法一定会漏（这个函数已经被挑出过四轮「又发现一种写法会漏」）：

| 第几道 | 挡什么 | 为什么需要它 |
| --- | --- | --- |
| 一 | 把 `fastpay-server.env` 里配的**那个真实数据库主机名**整个换掉 | 不认句式 —— 不管哪个驱动、用哪句话把地址打出来都挡得住。以后数据库挪到别的机器、改用机器名连，靠的就是这道 |
| 二 | 几种已知的固定话术：`jdbc:` 连接串、`Connection to 主机:端口 refused`、`connection to server at "主机"`、`could not translate host name "主机"`、`UnknownHostException: 主机` | 这些句式里的主机既没有 `jdbc:` 前缀、也不一定是数字 IP，只靠第一、三道会漏 |
| 三 | IPv6、数字 IP，以及「带点的机器名:端口」这种**形状** | 兜底。认形状而不是认句式，才跳得出「又发现一种写法会漏就再加一条」的死循环 |

**有两样是特意不遮的**，遮了日志反而没人看得懂：

- `127.0.0.1` —— 本机地址，人人都一样，不是内网拓扑
- `pay.copliot.cloud` —— 公开域名，[敏感信息怎么处理](SECRETS.md) 里明写「放心写」

堆栈里的 `HikariPool.java:554` 是源码行号不是地址，也特意避开了。

### 改了这个脚本？先跑一遍自测

`deploy/verify-release.sh` 改完之后、装到服务器上之前，先在本地跑这一条：

```bash
bash deploy/verify-release.test.sh
```

全过退出码是 0，有一条不过就是 1，屏幕上会指出是哪一条。**不需要服务器、不需要数据库、不需要 root**，几秒钟跑完。

它盯的主要是遮蔽那段 —— 那段是专门用来防泄露的，**正则动一个字符就可能开一个口子，而口子不会自己喊疼**。测试的做法是把脚本里**真正的那几段代码原样抠出来**跑，不是另抄一份，所以脚本改了测试跟着一起变，不会出现「测的是另一份代码」。

抠代码靠的是脚本里那几个位置标记（`# ===== 遮蔽（mask）开始 =====` 这类）。如果你大改了脚本结构，测试会直接报「抠不到某段」而不是假装通过 —— 看到这句就去把测试里的标记对齐。

### 部署时记得写一句版本标记

上面「版本号对不对得上」这一项，靠的是服务器上的 `/opt/fastpay/DEPLOYED_VERSION` 文件。它是 [部署说明](DEPLOY.md) 第三节里正式的**第 4 步**，在重启后端之后、验证之前：

```bash
ssh root@<服务器> "echo v1.6.0 > /opt/fastpay/DEPLOYED_VERSION"
```

**写错了会怎样**：比漏写更麻烦。漏写脚本会当场报错，写错了脚本反而是绿的 —— 直到出事那天，
有人照着这个文件去决定「退回哪一版」，才发现指错了地方。所以写的必须是**你刚刚实际传上去的那一版**，
不是别人汇报里的那一版。（2026-08-20 真出过：文件写着 `v1.5.1`，实际程序和库都已经是 `v1.6.0` 了，见 MTM-210）

**漏写了会怎样**：只要你给脚本传了版本号（正常都会传），脚本就会**直接判失败** —— 你要它核对是不是这一版，它却核不了，这种情况报「全绿」是骗人。只有在你压根没传版本号的时候，它才降级成提醒一句。

## 第二步：登进去点一遍

脚本能确认「系统活着、版本对、结构对」，**确认不了「这一版新改的功能到底对不对」**。这一步只能人来。

### 用哪个账号

**用验证专用的测试商户，不要用需求方本人的账号。**

> ✅ 这个商户需求方已经建好了，2026-08-20 用它把下面整条路实跑过一遍。

| 问题 | 答案 |
| --- | --- |
| 账号在哪 | 商户端 https://pay.copliot.cloud/fastpay-merchant/ |
| 账号叫什么、口令是什么 | 服务器上 `/root/fastpay-ops/credentials.md`，自己 SSH 上去看。**取不到就说明这台机器重建过**，找需求方要一次 |
| 为什么不用需求方的账号 | 他那个是**真实商户**，里面是真实交易数据。验证不该碰真实数据，详见 [敏感信息怎么处理](SECRETS.md) 第五节 |

### 测试数据自己造，不用等谁

这个测试商户是**空白**的，但它自己就能造出各种状态的订单，全程不需要真钱、也不需要管理员账号。

**⚠️ 头一次用这个商户，前三步必须都做完，缺一步下单就会失败。** 这是 2026-08-20 实测踩出来的 —— 只建了店铺就去下单，会报 `暂无可用的收款通道，请联系商户`，很容易误以为是系统坏了：

1. **建店铺** —— 商户端「店铺管理」（`POST /api/merchant/shop`，只有 `shopName` 必填）
2. **建收款通道** —— 商户端「通道管理」（`POST /api/merchant/channel`，必填 `channelName` + `payType`）
3. **建收款码** —— 商户端「收款码管理」（`POST /api/merchant/qrcode`，必填 `shopId` + `channelId`；验证用的话 `qrcodeUrl` 随便填个占位串就行，反正不会真去扫）

> 这三样**只要建一次**，以后每次发版直接从下一步开始。

4. **下单** —— `POST /api/pay/create`，订单进入「待支付」。签名怎么算、完整 curl 例子见 [接口文档](API.md) 第八节和「发起第一笔支付」那一段
5. **改状态** —— 商户端「订单管理」页面，待支付的订单上有「确认」和「关闭」两个按钮，点一下就变成「已支付」或「已关闭」

**订单状态的编号别记错**（筛选时要用，很容易搞混）：

| 编号 | 含义 | 怎么造出来 |
| --- | --- | --- |
| `0` | 待支付 | 下单后默认就是 |
| `1` | 已支付 | 点「确认」 |
| `2` | **已过期** | 放着不管，等超时任务扫到（默认 3 分钟） |
| `3` | **已关闭** | 点「关闭」 |

> ⚠️ `2` 是**已过期**不是已关闭，已关闭是 `3`。按 `2` 去筛「已关闭」会查出 0 条，看起来像功能坏了，其实是编号记错了。

> 💡 `v1.3.0` 那次卡住的正是「商户订单筛选」—— 用这个办法可以完整复现并验证。2026-08-20 实测走通过：造出待支付 / 已支付 / 已关闭三笔，按状态、支付方式、商品名、商户订单号分别筛，以及「搜一个不存在的订单号必须返回 0 条」这个关键回归点，全部正常。

### 验完之后

**验证数据留着就行，不用清理** —— 这个商户是隔离的，它的订单不会混进任何真实商户的数据里，也不影响统计。

**账号要不要停用？** 想停的话得请需求方在管理后台点一下 —— **停用商户是管理员权限，运维自己做不到**（`PUT /api/admin/merchant/{id}/status`，商户端没有对应接口）。

实际上不停用也行，风险很低：它没有真实交易数据，收款通道也是个假的占位配置，真收不到钱。**但它在自己范围内是全权限的，用的人自觉只看不改。**

## 这套办法验不了什么（别误以为全包了）

说在前面，免得踩空：

1. **管理后台自己的功能，验不了。**
   比如商户管理页、渠道配置页、控制台统计改了 —— 那需要第二个管理员账号，而这个系统**没有「新建管理员」的功能**，建它必须手工往数据库塞一行。这条红线暂时不破。
   **撞上这种情况怎么办**：只能请需求方本人点一下，或者单独立项做「管理员角色权限」的改造。

2. **真实支付链路，验不了。**
   扫码真付钱、收到真实到账通知之后页面自动跳转 —— 这些要真实收款渠道配合。测试商户点「确认支付」走的是另一条路，**不会触发自动跳转**，别拿它测这个功能（详见 [部署说明](DEPLOY.md) 第七节第 1 条）。

3. **「只能看不能改」的账号，现在做不出来。**
   系统没有角色权限这一档，测试商户在自己的范围内是全权限的。用的人自觉只看不改。

---

## 出问题了怎么办

- 脚本报 ❌：按提示逐条处理，处理完重跑脚本
- 处理不了：**回退到上一个 tag**，步骤见 [部署说明](DEPLOY.md) 第四节。回退只换 jar 和前端，不用动数据库，10 分钟内能完成
- 拿不准要不要回退：先回退，再慢慢查。**线上不是查问题的地方**
