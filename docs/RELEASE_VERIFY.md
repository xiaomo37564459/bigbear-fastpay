# 发完版怎么确认「真的发好了」

每次把新版本发到线上之后，按这一页走一遍。**一共两步**：

1. **跑一条命令** —— 机器能替你确认的事，它一次全查完
2. **登进去点一遍** —— 这一版改了什么，就点什么。这一步机器替不了

两步都过了，才算发好了。

> 这套办法是 MTM-190 定下来的（需求方选了方案 D）。核心思路是：
> **能自动化的全自动化，不需要任何账号；实在要人点的那一小块，用一个不含真实数据的验证专用商户去点。**

---

## 第一步：跑验证脚本

在自己电脑上、仓库根目录执行，把版本号换成这次发的：

```bash
ssh root@<服务器> 'bash -s v1.5.0' < deploy/verify-release.sh
```

已经登在服务器上了也行：

```bash
bash /root/fastpay-ops/verify-release.sh v1.5.0
```

它会依次查这些，**任何一项 ❌ 就会以退出码 1 结束**，可以直接串在部署命令后面：

| 查什么 | 为什么要查 |
| --- | --- |
| 后端服务在不在跑 | 最基本的 |
| **服务启动时间是不是晚于 jar 修改时间** | 换了 jar 忘了重启 —— 最常见也最难发现的一种「发了个寂寞」 |
| 服务器记的版本号和你要发的对不对得上 | 防止传错文件、传漏文件 |
| 后端本机健康检查 200 | 程序自己活着 |
| 两个前端页面公网 200 | 用户真的打得开 |
| 公网健康检查 200 | nginx 转发也是通的 |
| 接口文档对外是 404 | 排查问题时打开过，忘了关回去 |
| 有没有全局可写的文件 | Windows 打的 tar 包解压到 Linux 会变成谁都能改，支付页被人换掉都发现不了 |
| 数据库连得上、迁移到位 | 该跑的迁移脚本跑了没有 |
| 最近日志里有没有 ERROR | 起来了不代表没问题 |

脚本**只读**：不写数据库、不改配置、不重启服务。它会读 `/etc/fastpay/fastpay-server.env` 拿数据库地址，但绝不会把里面的值打印出来。

### 部署时记得写一句版本标记

上面「版本号对不对得上」这一项，靠的是服务器上的 `/opt/fastpay/DEPLOYED_VERSION` 文件。它是 [部署说明](DEPLOY.md) 第三节里正式的**第 4 步**，在重启后端之后、验证之前：

```bash
ssh root@<服务器> "echo v1.5.0 > /opt/fastpay/DEPLOYED_VERSION"
```

**漏写了会怎样**：只要你给脚本传了版本号（正常都会传），脚本就会**直接判失败** —— 你要它核对是不是这一版，它却核不了，这种情况报「全绿」是骗人。只有在你压根没传版本号的时候，它才降级成提醒一句。

## 第二步：登进去点一遍

脚本能确认「系统活着、版本对、结构对」，**确认不了「这一版新改的功能到底对不对」**。这一步只能人来。

### 用哪个账号

**用验证专用的测试商户，不要用需求方本人的账号。**

> ⏳ **这个测试商户还没建，在等需求方在管理后台创建。** 建好之前，这一节写的办法还用不了 —— 第一步那个脚本不受影响，照样能跑。

| 问题 | 答案 |
| --- | --- |
| 账号在哪 | 商户端 https://pay.copliot.cloud/fastpay-merchant/ |
| 账号叫什么、口令是什么 | 需求方建好之后，口令会放到服务器上的 `/root/fastpay-ops/credentials.md`，自己 SSH 上去看 |
| 为什么不用需求方的账号 | 他那个是**真实商户**，里面是真实交易数据。验证不该碰真实数据，详见 [敏感信息怎么处理](SECRETS.md) 第五节 |

### 测试数据自己造，不用等谁

这个测试商户是**空白**的，但它自己就能造出各种状态的订单，全程不需要真钱、也不需要管理员账号。

**⚠️ 头一次用这个商户，前三步必须都做完，缺一步下单就会失败。** 这是 2026-08-20 实测踩出来的 —— 只建了店铺就去下单，会报 `暂无可用的收款通道，请联系商户`，很容易误以为是系统坏了：

1. **建店铺** —— 商户端「店铺管理」（`POST /api/merchant/shop`，只有 `shopName` 必填）
2. **建收款通道** —— 商户端「通道管理」（`POST /api/merchant/channel`，必填 `channelName` + `payType`）
3. **建收款码** —— 商户端「收款码管理」（`POST /api/merchant/qrcode`，必填 `shopId` + `channelId`；验证用的话 `qrcodeUrl` 随便填个占位串就行，反正不会真去扫）

> 这三样**只要建一次**，以后每次发版直接从下一步开始。

4. **下单** —— `POST /api/pay/create`，订单进入「待支付」。签名怎么算、完整 curl 例子见 [接口文档](API.md) 第八节和「发起第一笔支付」那一段
5. **改状态** —— 商户端「订单管理」页面，待支付的订单上有「确认」和「关闭」两个按钮，点一下就变成「已支付」或「已关闭」

**订单状态的编号别记错**（筛选时要用，很容易搞混）：

| 编号 | 含义 | 怎么造出来 |
| --- | --- | --- |
| `0` | 待支付 | 下单后默认就是 |
| `1` | 已支付 | 点「确认」 |
| `2` | **已过期** | 放着不管，等超时任务扫到（默认 3 分钟） |
| `3` | **已关闭** | 点「关闭」 |

> ⚠️ `2` 是**已过期**不是已关闭，已关闭是 `3`。按 `2` 去筛「已关闭」会查出 0 条，看起来像功能坏了，其实是编号记错了。

> 💡 `v1.3.0` 那次卡住的正是「商户订单筛选」—— 用这个办法可以完整复现并验证。2026-08-20 实测走通过：造出待支付 / 已支付 / 已关闭三笔，按状态、支付方式、商品名、商户订单号分别筛，以及「搜一个不存在的订单号必须返回 0 条」这个关键回归点，全部正常。

### 验完之后

**验证数据留着就行，不用清理** —— 这个商户是隔离的，它的订单不会混进任何真实商户的数据里，也不影响统计。

**账号要不要停用？** 想停的话得请需求方在管理后台点一下 —— **停用商户是管理员权限，运维自己做不到**（`PUT /api/admin/merchant/{id}/status`，商户端没有对应接口）。

实际上不停用也行，风险很低：它没有真实交易数据，收款通道也是个假的占位配置，真收不到钱。**但它在自己范围内是全权限的，用的人自觉只看不改。**

## 这套办法验不了什么（别误以为全包了）

说在前面，免得踩空：

1. **管理后台自己的功能，验不了。**
   比如商户管理页、渠道配置页、控制台统计改了 —— 那需要第二个管理员账号，而这个系统**没有「新建管理员」的功能**，建它必须手工往数据库塞一行。这条红线暂时不破。
   **撞上这种情况怎么办**：只能请需求方本人点一下，或者单独立项做「管理员角色权限」的改造。

2. **真实支付链路，验不了。**
   扫码真付钱、收到真实到账通知之后页面自动跳转 —— 这些要真实收款渠道配合。测试商户点「确认支付」走的是另一条路，**不会触发自动跳转**，别拿它测这个功能（详见 [部署说明](DEPLOY.md) 第七节第 1 条）。

3. **「只能看不能改」的账号，现在做不出来。**
   系统没有角色权限这一档，测试商户在自己的范围内是全权限的。用的人自觉只看不改。

---

## 出问题了怎么办

- 脚本报 ❌：按提示逐条处理，处理完重跑脚本
- 处理不了：**回退到上一个 tag**，步骤见 [部署说明](DEPLOY.md) 第四节。回退只换 jar 和前端，不用动数据库，10 分钟内能完成
- 拿不准要不要回退：先回退，再慢慢查。**线上不是查问题的地方**
