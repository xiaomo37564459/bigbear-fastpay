# 提交代码后的自动检查

## 这东西是干嘛的

以前经常出现这种返工：开发同学在**自己拉分支那天的主干**上把测试跑绿了，交上来验收的时候才发现，
合到**今天最新的主干**上其实是红的。每发现一次就白白多转一轮，而且只有人工才发现得了。

现在只要往 PR（代码提交页面）上推代码，机器就会自动做三件事：

1. 把当天最新的主干（`master`）合进你的分支
2. 合不上（有冲突）就直接在 PR 上报「跟主干冲突了」，并列出打架的文件
3. 合得上就跑一遍全部测试，绿还是红直接标在 PR 上

**本期只报告，不拦截。** 这个检查红了**不会**挡住合并 —— 仓库上没有配置任何「必须绿才能合并」的规则，
分支保护也没动。它只负责让你早点看见问题。

## 配置文件在哪

| 文件 | 作用 |
| --- | --- |
| `.github/workflows/pr-check.yml` | 主配置：PR 上跑的那五项（合主干 + 后端 + 前端 + 运维脚本自测 + 结论） |
| `.github/workflows/conflict-check.yml` | 每次推代码都查一下「跟主干还合得上吗」，原因见下面那节 |
| `.github/workflows/pr-overlap.yml` | 撞车提醒：你改的文件别人也在改，见下面那节 |
| `.github/scripts/pr-overlap.sh` | 撞车提醒的实现（`pr-overlap.test.sh` 是它的自测） |
| `.github/actions/merge-master/action.yml` | 「合最新主干」这一步的实现，几个检查共用同一份 |
| `scripts/ci-local.sh` / `scripts/ci-local.ps1` | 本地跑同样一套检查的脚本 |

## 怎么触发

- **自动**：任何一个 PR 新开、或者往分支推了新代码，就自动跑一次。不用做任何事
- **手动**：GitHub 仓库页 → 上方 **Actions** 标签 → 左侧选 **PR 检查（先合最新主干再跑测试）** →
  右侧 **Run workflow** → 选一个分支 → 跑。（手动触发的按钮要等这份配置合进 `master` 之后才会出现）

同一个分支连着推好几次，只保留最后一次的结果，前面的会自动取消。

## 从哪看结果

打开那个 PR，拉到最下面的检查列表：

| 检查项 | 跑的是什么 |
| --- | --- |
| `跟主干合得上吗` | 每次推代码都查。**真冲突的时候，只有这一项会红**，原因见下一节 |
| `有没有人在改同一批文件` | 撞车提醒，见下面那节。**永远不会红**，只在 PR 上留一条评论 |
| `1·先合最新主干` | 把主干最新代码合进来，然后才跑测试 |
| `2·后端测试 fastpay-server（MySQL + PostgreSQL）` | `mvn -B test`，含 MySQL 和 PostgreSQL 两套端到端测试 |
| `3·前端测试 (fastpay-admin)` / `(fastpay-merchant)` | `npm test` + `npm run build` |
| `4·运维脚本自测（发版验证 + 生产操作锁 + 撞车提醒）` | 三个运维脚本各自的自测，纯 bash，十几秒 |
| `5·一句话结论` | 一句人话总结这次是绿是红 |

### 为什么冲突要单独开一项检查

GitHub 有个坑：一个 PR 一旦跟主干**真的冲突**了，它就**根本不会**去跑 PR 上那套检查
（就是上面 1~4 项）。因为 PR 的检查是跑在「你的分支和主干合好之后的临时版本」上的，
合都合不出来，它干脆就不跑了 —— PR 底下一项检查都看不到，像是坏了一样。

所以「跟主干合得上吗」这一项挂在**推代码**这个时机上：推代码不需要先合并，一定跑得起来。
它很快（十几秒），只做一件事：把主干合进来试试，合不上就红，并列出打架的文件和解决办法。

冲突的时候你会看到两样东西：GitHub 自己在 PR 顶部弹的冲突提示，加上这一项红掉的检查。

点任意一项右边的 **Details** 就能进去看日志。几个要点：

- **这次基于哪个主干版本跑的**，写在每一项的日志开头，也写在运行页面顶部的摘要（Summary）里，
  长这样：`主干（master）版本号 : d1097527a3fe...`，可以直接点开看那笔提交
- **红了怎么定位**：看是哪一项红的就点哪一项。后端测试红了还可以在运行页面底部下载
  `后端测试报告-surefire` 附件，里面是每条测试的详细报错
- 前端那两项就算测试挂了也会照样打一次包，好让你一次看清「是测试挂了，还是连编译都过不去」

## 撞车提醒：你改的文件，别人也在改

### 这是干嘛的

2026-08-20 那天出过一件事：**同一件事被不同的人重复开工了三次**，而且三次都是各自把活干完、
开了 PR 之后才被人事后巡查发现的 ——

- 「数据库脚本改名」开了 3 个 PR（`#29`、`#33`、`#34`），改的是同一组文件
- 「发版验证脚本加固」三分钟之内开了 3 个 PR（`#30`、`#31`、`#32`），改的是同一个脚本

每个人自己都没做错：都是发现了毛病、自己动手。问题是**中间没有任何东西提醒他们「这件事已经有人在做了」**。

现在有了：一开 PR（或者往分支推了新代码），机器就会拿你改的文件跟**其他所有还开着的 PR** 比一遍，
撞上了就在你这个 PR 底下留一条评论，写清楚 **跟哪几号撞了、撞在哪几个文件上、对方那条是谁开的、标题是什么**。

### ⚠️ 它只提示，不拦你

撞车**不会**让任何检查变红，更不会挡住合并。两路人正当地改同一个文件是常事（比如都往同一份
配置里加一行），一刀切拦死会误伤。所以这一项在 PR 的检查列表里**永远是绿的**，
它唯一做的事就是留那条评论。

### 你会看到什么

撞了的时候，PR 底下会出现一条这样的评论：

> ## ⚠️ 你改的文件，还有别人也在改
>
> 还有 **2 个**没合并的提交，跟你动了同一批文件（共 2 个文件撞上）。
>
> ### [#30](#) 发版验证脚本加固：日志别漏数据库地址 · @liangyun
> 撞了 2 个文件：
> - `deploy/verify-release.sh`
> - `docs/DEPLOY.md`
>
> ### [#31](#) 没装 psql 时会误报连得上 `草稿` · @gujian
> 撞了 1 个文件：
> - `deploy/verify-release.sh`

几个要点：

- **每推一次代码，这条评论会原地更新**，不会越堆越多
- **撞车解除了，这条会自己改成「✅ 没跟别人撞」**，不会留一条过期的提醒在那儿误导人
- 从来没撞过的 PR **不会**收到任何评论（不刷屏）
- **草稿状态的 PR 也算**。别人刚开个草稿占坑，也是「已经有人在做了」
- 评论里带 `@对方` —— 对方也会收到通知，所以两边都会知道撞上了

### 看到之后怎么办（三选一，自己判断）

1. **确实是同一件事** → 在评论下面回一句，商量好谁来做，另一个关掉。别两边都改
2. **是两件不同的事，只是碰巧动到同一个文件** → 不用管，继续。合并的时候留意解冲突就行
3. **拿不准** → 在对应的 issue 里问一句总指挥，别自己闷头往下做

### 怎么触发

- **自动**：PR 新开 / 重开 / 从草稿转正式 / 推了新代码，都会跑一次。不用做任何事
- **手动**：GitHub 仓库页 → **Actions** → 左侧选 **撞车提醒（你改的文件别人也在改）** →
  **Run workflow** → 在「要检查哪个提交」里填 PR 号（比如 `34`）→ 跑
- **本地试**（不发评论，只把评论正文打出来看看）：

  ```bash
  gh auth login                                        # 没登录过才要
  bash .github/scripts/pr-overlap.sh run 34 --dry-run
  ```

### 为什么它同时挂在「推代码」和「开 PR」两个时机上

跟上面「冲突要单独开一项检查」是同一个坑：**PR 一旦跟主干真的冲突，GitHub 就不跑 PR 上的检查了。**
而「两个人改同一批文件」恰恰最容易冲突 —— 最该提醒的时候反而提醒不了。
推代码这个时机不需要先合并，一定跑得起来，正好补上。

两个时机前后脚各触发一次，但同一个分支只保留最后一次（前面的自动取消），所以评论只会有一条。

### 已知的边界，不是 bug

- **先开的那个 PR 当时不会被通知。** 比如 `#30` 先开、`#31` 后开，撞车提醒发在 `#31` 上。
  `#30` 要等下一次推代码才会自己发现（不过评论里 `@` 了 `#30` 的作者，他会收到通知）
- **只跟合到同一个目标分支的 PR 比。** 合到不同分支本来就是两条线
- **仓库里开着的 PR 超过 60 个**时，只比最近更新的那 60 个，并且会在评论里写明「还有 N 条没比到」
- **fork 过来的 PR 发不出评论**（GitHub 给的令牌是只读的）。日志里会写明原因，不影响任何检查结果

### 改这个脚本之前

先跑自测，不联网、十几秒：

```bash
bash .github/scripts/pr-overlap.test.sh
```

这个自测在每个 PR 上也会自动跑一遍（`4·运维脚本自测` 那一项里）。它盯的是两件事：
**该报的必须报出来**（漏报是安安静静的，代价就是又一次三个人干同一件事），
以及**任何情况下都不许拦人**。

## 本地怎么跑同样的测试

一条命令（在仓库根目录）：

```bash
# Linux / macOS / Windows 的 Git Bash
bash scripts/ci-local.sh
```

```powershell
# Windows PowerShell
powershell -ExecutionPolicy Bypass -File scripts\ci-local.ps1
```

脚本做的事和 CI 完全一样：抓最新主干 → 合进来 → 跑后端 `mvn -B test` → 跑两个前端的
`npm ci && npm test && npm run build`。

**它不会动你现在的工作目录** —— 合并是在一个临时目录里做的，跑完自动删掉。
每次重新装依赖有点慢，想让依赖留着下次接着用，就指定一个固定目录：

```bash
CI_LOCAL_DIR=../fastpay-ci-local bash scripts/ci-local.sh
```

```powershell
$env:CI_LOCAL_DIR = "..\fastpay-ci-local"
powershell -ExecutionPolicy Bypass -File scripts\ci-local.ps1
```

不想用脚本、只想手动跑其中一块的话：

```bash
cd fastpay-server   && mvn -B test
cd fastpay-admin    && npm ci && npm test && npm run build
cd fastpay-merchant && npm ci && npm test && npm run build
```

## 环境说明

- 检查跑在 GitHub 提供的 Ubuntu 机器上，用 JDK 17（temurin）和 Node 20
- 两套端到端测试**不需要 Docker、也不需要机器上装数据库**：测试自己会临时拉起一个真的 MariaDB
  （MySQL 协议兼容，靠 MariaDB4j）和一个真的 PostgreSQL（靠 zonky embedded-postgres），跑完自动销毁
- **机器时区设成了东八区（`TZ: Asia/Shanghai`）**，跟开发同学的机器、跟配置里写死的
  `Asia/Shanghai` 保持一致，见下面一节
- 这个检查只读代码、只跑测试，**不碰服务器、不碰任何数据库、不发布任何东西**

### 为什么要专门把 CI 机器的时区调成东八区

GitHub 的机器默认是 UTC（零时区）。不调的话，`MySqlFullFlowTest` 里「订单超时自动关单」那两条
测试会挂：测试往数据库写过期时间用的是机器的本地时间，而 MySQL 连接串里写死了
`serverTimezone=Asia/Shanghai`，两边差 8 小时，本该过期的订单就没过期。PostgreSQL 那条路径的连接串
没有这个参数，所以不受影响 —— 这也是为什么只有 MySQL 那一半会挂。

把 CI 机器调成东八区，是为了让「本地绿 = CI 绿」，**不是绕开测试**。

⚠️ 但这件事本身是个隐患：**真把服务部署到一台 UTC 时区的服务器上，同样的问题会在生产上重现**
（订单该超时的不超时）。这个已经单独提出来给后端跟进，不在本期 CI 的范围内。上线前请确认服务器
时区是东八区：`timedatectl` 看一眼，不对就 `sudo timedatectl set-timezone Asia/Shanghai`。
